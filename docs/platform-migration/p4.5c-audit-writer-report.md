# P4.5C — Complete Audit Writer Platform Adoption

Platform 2.3.0, consumed from GitHub Packages. No workspace references, no tarballs, no
overrides, no local paths.

## The division that resulted

The Platform owns **sealing**: canonical material, digest, chain linkage, sequence advance,
format stamp. Munaxa Docs owns **ordering** and **vocabulary**: the per-tenant advisory lock, the
gap-free `tail + 1` allocation, the UUID v7 identifier strategy, the three historical canonical
formats, and the document-management action catalogue.

That split is not a compromise. `appendChained()` is specified so the adapter reads the head,
calls `seal`, and persists what comes back — which is exactly where this product's guarantees
live, and the Platform never asked for them.

## What needed care

### Mint before hash

All three Docs formats cover the event id. An id derived from the digest — the Platform's own
default — is therefore circular. Platform 2.3.0's `generateId` hook runs *before* hashing and
passes the id to the format as `recordId`, which is what makes this append path expressible at
all. Without P3.8 this phase could not have been done without weakening something.

### The instant

`AuditService` reads its clock once per write and uses that value for both `recordedAt` and the
argument to `generateId`. For a synchronous write that is microseconds from `occurredAt`. For a
buffered read it is not: a view recorded at 09:30 is flushed seconds or minutes later, so a
singleton service would mint that record's UUID v7 from the *flush* instant. Identifiers would
sort by when the batch went out rather than by when the document was read — the one property
`13-audit-architecture.md` §5 asks the buffer to preserve.

`createDocsAuditService(repository, occurredAt)` binds the instant at construction instead. The
service is a plain object with no I/O in its constructor, so one per append costs nothing
measurable against the round trip it is about to make, and there is no shared mutable "current
instant" to get wrong under concurrency.

The integration test `keeps the instant of the read, not the instant of the flush` passes.

### The batch

The read buffer exists so that a hundred page views cost one advisory lock rather than a hundred.
Routing each buffered event through the singleton adapter would have re-read the head and issued
a separate `INSERT` per event — the exact cost the buffer was built to avoid.

`BatchedPlatformAuditRepository` takes the lock and reads the head once, lets the Platform's
sealer advance it in memory, and issues the whole batch as one `appendMany`. That is not a
weakening: the lock is held for the whole transaction, so no other writer can advance the chain
underneath, and every record still chains to the digest of the one before it. It is the same
argument `appendMany` already relied on.

One instance per flush, deliberately not `@Injectable()`: a shared instance would have shared
mutable chain state.

### Genesis

The store's empty chain is `{ sequence: 0n, hash: GENESIS_HASH }`; the Platform's is `null`.
Handing the Platform the literal zero head keeps the first record's sequence a `bigint` rather
than the number `1` that `null` would produce, and the Docs formats hash `previousHash ??
GENESIS_HASH`, so 64 zeros and `null` canonicalise identically. Only one representation reaches
the `char(64)` column.

## The vocabulary

`AuditEntry.action` and `AuditEventRecord.action` were `string`. They are now `DocsAuditAction` —
a closed union of 80 members: the 81 entries across nineteen catalogues in fifteen files (two of
which, `SETTING_CHANGED` and `DELEGATION_USED`, two modules deliberately share), plus
`TENANT_PROVISIONED`, which was an inline string literal with no catalogue at all.

It lives in `@edms/domain` rather than `core/audit`, because no file in `apps/api` may import
every catalogue: `core/` may not depend on a module, and a module may not reach into another
module's `domain/`. Both rules are enforced in `eslint.config.mjs`, and both are right.

The literals are repeated rather than derived, because deriving would mean moving the catalogues
out of the modules that own them — and the catalogues carry the reasoning for the vocabulary
(why `RULE_CHANGED` is not a `POLICY_CHANGED`, why a delegation is not a user). The duplication
cannot drift: every catalogue now ends `} as const satisfies Record<string, DocsAuditAction>`, so
an action added to a module and not to the union is a compile error at the line that added it.

**Reads are permissive where writes are strict.** The append path refuses an action outside the
vocabulary; `toRecord` casts. The table is append-only and outlives its code, so a row written
under an action later retired must stay readable — otherwise the trail stops being evidence the
moment the vocabulary changes.

Two integration specs used invented action markers (`'FIRST'`, `'CONCURRENT_3'`) as chain
labels. They now use real actions. The tamper simulation is *stronger* for it: the altered value
is one the writer could genuinely have produced, so the digest is the only thing catching it.

## Historical compatibility

No digest changed. `DOCS_CANONICAL_V3` reproduces `chainHash(…, CHAIN_HASH_V3)` byte for byte.

`platform-canonical.spec.ts` asserts this against `chainHash` **itself** rather than against a
stored fixture, because `chainHash` is what wrote every row in every deployment. If the two ever
disagree the rows cannot be rehashed — the table refuses `UPDATE` to every role including the
owner — so disagreement means the evidence is gone. That makes it the highest-stakes test here,
and it is why `chainHash` was kept rather than deleted.

## What was removed

- The `chainHash` append path in `ChainedAuditWriter` — the writer now calls `audit.write()`.
- The `chainHash` append path in `BufferedReadAuditWriter`, including its hand-rolled
  `previousHash`/`sequence` loop and its parallel `material` object.
- The duplicate `AuditEventRecord` assembly in both writers: one description of the act now
  produces both the digest and the row.
- `BufferedEvent.eventId` — the id is minted by the Platform at seal time, from the same instant.

`chainHash` itself survives, and is not obsolete: the verification path still uses it. Keeping
one function rather than two implementations of the same digest is what lets the compatibility
test compare them directly.

- `lands chained and contiguous, a batch at a time under one lock`
- `keeps the instant of the read, not the instant of the flush`
- `refuses an update or a delete, even for the owner`
- `detects a row whose field was altered, over the digest the database stored`
- `verifies a chain that spans both digest versions`
- `refuses to write outside a transaction, rather than opening one of its own`

# Repository audit — remaining Platform adoption opportunities

Nothing below was migrated in this phase. This is a prioritised list with recommendations.

## P1 — `@munaxa/config` (not adopted)

`core/config/configuration.ts` is **1,256 lines** of hand-rolled environment parsing against
`@munaxa/config`'s 555-line schema DSL plus secret providers, feature flags and tenant-layered
resolution.

This is the largest single duplication left in the repository, and the one with the clearest
payoff: the Platform's schema reports *every* configuration problem at once at startup rather
than the first one, which is the difference between one deploy cycle and six.

It has been unblocked since Platform 2.1.0 added env aliases, nested objects, schema-level
refinement and extension schemas — the four gaps the original survey found.

**Recommendation:** next phase. Migrate the schema first and keep the exported `AppConfig` shape
identical, so nothing downstream moves. `SecretsPort` and the tenant layering are separable
follow-ups.

## P2 — Audit verification (`@munaxa/audit`'s `verifyChain`)

`audit-verification.service.ts` (315 lines) and `hash-chain.ts`'s `verifyChain` still recompute
the chain locally. The Platform's `verifyChain` already dispatches per record on `formatVersion`,
and the three Docs formats are already registered — this phase built everything it needs.

This is the natural completion of the audit migration and is deliberately left out of P4.5C,
which was scoped to the writer.

**Recommendation:** next phase, immediately after or alongside P1. Note that the product's result
shape (`BreakReason`: `DIGEST_MISMATCH` / `LINK_MISMATCH` / `SEQUENCE_GAP`) is richer than the
Platform's `reason` string, and the evidence bundle's manifest depends on `attestedFields()`.
Either map the Platform's reason back, or propose the richer shape as a Platform enhancement —
the distinction between "a field was altered" and "a record was removed" is a different
accusation and an evidence bundle should not lose it.

## P3 — `@munaxa/security` (not adopted)

`core/security/` is 110 lines against the Platform's 1,200: `rate-limit.ts` (32) vs
`ratelimit.ts` (310, distributed), `security.headers.ts` (33) vs `headers.ts` (220).

The Platform additionally offers CSRF, input normalization, risk scoring and threat tripwires,
which this product has none of.

**Recommendation:** after P1. Take **distributed rate limiting first** — the local one is
per-process, so the documented limit is silently multiplied by the replica count, which is a real
control gap rather than a duplication. Headers are a small, safe second. Risk and threats are new
capability, not adoption, and belong in a product decision rather than a migration phase.

## P4 — MFA / TOTP (`@munaxa/auth`)

`modules/identity/domain/totp.ts` (213 lines) duplicates `auth/src/mfa.ts`'s `totpCode`,
`verifyTotp`, `generateTotpSecret` and `totpUri`.

**Recommendation:** medium priority, and **verify compatibility empirically before migrating** —
exactly as the refresh-token hash was proven before P4.4B. Every enrolled authenticator in every
deployment depends on the secret encoding and the step window matching. A mismatch signs out
every user with MFA enabled, and unlike a password there is no fallback path.

## P5 — `LoginService` and account lockout (`@munaxa/auth`)

Deferred from P4.4B and still open. The Platform's `LoginService` brings account lockout, which
this product does not have.

**Recommendation:** this is a **feature decision, not a migration**. Lockout changes observable
behaviour for end users and needs a product owner, not a phase brief.

## P6 — Refresh-token pepper

The migration to `@munaxa/auth` deliberately kept the un-peppered `sha256(token)` hash, because
introducing the pepper would invalidate every stored refresh token and sign out every user.

**Recommendation:** low priority, and it needs a **dual-read grace period** — accept both hashes
for one refresh-token lifetime, then drop the old. Not a phase on its own; fold it into whichever
phase next touches the token store.

## P7 — `@munaxa/notifications` (not adopted)

`modules/notification/` is a substantial product module (digests, recipient visibility,
admin settings) against a Platform package scoped narrowly to *security* notifications.

**Recommendation:** **do not migrate.** The overlap is small and the Platform's guarantees
(critical messages bypass deduplication, credential-shaped payloads are refused) apply to a
different problem. Revisit only if this product starts sending security notifications of its own.

## P8 — `MetricsPort`

`core/observability/metrics.ts` (154 lines) implements a label-cardinality catalogue the Platform's
two-method `MetricsPort` does not have.

**Recommendation:** **do not migrate.** The local implementation is strictly richer, and the
enforced label catalogue is a real control. If anything, propose the cardinality guard *to* the
Platform.

## P9 — Legacy scrypt verifier

Verify-only, and cannot be removed until no `scrypt$` rows remain.

**Recommendation:** blocked on data, not code. Add a migration-progress query to the operations
runbook so the removal has a trigger rather than a hope.

## Summary

| Priority | Item | Size of duplication | Recommendation |
|---|---|---|---|
| P1 | `@munaxa/config` | ~1,250 lines | Migrate next |
| P2 | Audit verification | ~400 lines | Migrate next |
| P3 | Distributed rate limiting | ~30 lines, real control gap | Migrate after P1 |
| P4 | TOTP | ~210 lines | Migrate, prove compatibility first |
| P5 | `LoginService` / lockout | — | Product decision |
| P6 | Refresh-token pepper | — | Fold in, needs dual-read |
| P7 | `@munaxa/notifications` | — | Do not migrate |
| P8 | `MetricsPort` | — | Do not migrate; propose upstream |
| P9 | Legacy scrypt verifier | — | Blocked on data |

The pattern worth naming: four consecutive Platform releases were each unblocked by a missing
generic or injection point found by a consumer one release later. Surveying the consumer *before*
writing the Platform code caught three gaps before 2.1.0 and would have caught P-6 during P3.6
had Docs' `chainHash` been read then. P1 and P2 above should both begin with that survey.
