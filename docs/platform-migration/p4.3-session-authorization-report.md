## 1. RBAC migration report

### Completed — permission evaluation

`RbacGuard` evaluated permissions with a hand-rolled `Set.has`. It now calls `hasPermission` from
`@munaxa/rbac`, so the question "does this principal hold this permission" is answered the same way
in every Munaxa product.

**Proven equivalent before the change, not asserted after it.** All 37 of this product's permission
keys pass the platform grammar (`assertValidGrant` and `assertValidCheck`), and `hasPermission`
agrees with `Set.has` on every combination of held-versus-required across the full key set — 0
mismatches. Permission names, API responses and security semantics are unchanged.

Docs gains wildcard grants it does not use. That is upside rather than a change: a grant containing
no `*` matches exactly, which is what the old check did.

**A correction worth recording.** An early probe appeared to show the platform rejecting
`admin.roles:manage` as malformed. That key was one I invented for the probe — no Docs permission
contains a dot. Testing the real list instead of my example turned a false blocker into a safe
migration. It is in this report because the near-miss is the useful part: a limitation report based
on a fabricated input would have blocked this phase for no reason.

### Not started — and deliberately so

The rest of `@munaxa/rbac` does not fit this product's architecture, and forcing it would violate
this phase's own constraints.

| Platform component | Why not adopted |
| --- | --- |
| `PermissionResolver` | Docs resolves a user's permissions **at authentication** and carries them in the access token and `currentContext()`. The platform resolves **per request** from role storage behind a cache. Swapping changes token contents (an API change) and revocation latency (a security-semantics change) — both explicitly forbidden here. |
| `RoleHierarchy` | Docs has no role inheritance. `Role → RolePermission → UserRole` is flat by design. There is nothing to replace. |
| `PolicyEngine` | Docs has `policy.port.ts` (45 lines) plus `AclGuard` and `document-visibility` — but those evaluate **document ACLs**, which is document-management business logic, not platform authorization. It stays. |
| Decorators / guards | Docs' `@RequirePermissions` and `RbacGuard` integrate with Nest's `Reflector` and the local `PUBLIC_ROUTE` marker. The platform's equivalents are framework-agnostic. Replacing them changes the Nest wiring for no behavioural gain. |

Docs' pre-resolution design is deliberate and documented: changing a role's permissions bumps
`tokenVersion`, which re-evaluates every holder immediately. That is a different — and defensible —
answer to revocation latency than the platform's cache TTL.

**Deleted: nothing.** The only overlap was the evaluation call itself.

## 2. Session migration report — **blocked**

Per the phase rules: stop, document, do not work around.

**Docs has no session record.** There is no `Session` model. What exists is `SessionFamily` — a
refresh-token lineage — plus `RefreshToken`:

| `SessionFamily` | Platform `SessionRecord` |
| --- | --- |
| `id`, `tenantId`, `userId`, `createdAt` | same |
| `revokedAt`, `revokedReason`, `ipAddress`, `userAgent` | same |
| — | `lastSeenAt`, `idleExpiresAt`, `absoluteExpiresAt` |
| — | `authMethods`, `mfaSatisfied`, `tokenVersion`, `deviceId` |

The two are different concepts that share a word. `SessionFamily` tracks a token lineage so a
detected replay can revoke it; `SessionManager` manages a session lifecycle with idle and absolute
deadlines. Adopting the platform requires a new table, a schema migration, and rewiring the refresh
flow — and this phase forbids changing the refresh flow, forbids behaviour changes, and does not
authorise schema changes.

### The critical requirement, answered

> Distributed session limits MUST actually enforce limits. Never leave `SessionManager` in
> best-effort mode.

**Docs has no session concurrency limit today** — `maxConcurrent` appears nowhere in the codebase.
There is therefore nothing to enforce, and the requirement is satisfied in the only honest way
available: `SessionManager` was **not introduced at all**, so it cannot be sitting in best-effort
mode.

Introducing it would have meant adding a feature this product does not have, which is a behaviour
change rather than a migration. Had I adopted it without `createWithinLimit` or a `LockPort`, the
result would have been exactly the silent best-effort ship this phase prohibits.

**When session migration is attempted** (a later phase, with schema authority), it must land with
either a Prisma `createWithinLimit` or a `LockPort`, decided up front — not discovered afterwards.

## 3. LockPort adoption report — **not started, no usage to replace**

Stated explicitly, as the phase asks: **Munaxa Docs does not implement distributed locking.**

`ports/cache.port.ts` declares a `LockPort` and `Lease`, and `testing/fake-ports.ts` has a
`FakeLock` — but no production code acquires a lock. The port is declared and wired to nothing.

The apparent 38-file match for `LOCK_PORT` in the P4 survey was a false positive: `CLOCK_PORT`
contains `LOCK_PORT` as a substring. Real usage is zero.

There is consequently nothing to migrate, and inventing a use for the platform's `LockPort` to
justify adopting it would be the opposite of this phase's intent. The correct time to adopt it is
when something needs it — most likely session concurrency, which is blocked above.

The platform's `LockPort` is the better interface when that day comes: its `LockHandle` carries a
**fencing token**, so a holder that stalls past its lease cannot release a lock a second holder now
owns. The local `Lease` has no such concept.
