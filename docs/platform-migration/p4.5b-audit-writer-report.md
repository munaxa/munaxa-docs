# P4.5B — Audit writer & transaction integration

**Blocked.** Two Platform limitations prevent the writer from moving, and this phase forbids both
modifying the Platform and working around it in the product. No code was changed.

The good news first, because it inverts the risk the brief anticipated: **sequence allocation and
transaction participation are not the problem.** Both work under the current contract. What blocks
the writer is the event vocabulary and the record identifier — the two things P-7 and 2.1.0 solved
for other ports and did not finish for this one.

---

## 1. Audit Writer Migration Report — **Blocked**

### Blocker P-8 — the vocabulary parameter stops at `AuditRecord`

P-7 made `AuditRecord<TName>` generic and widened `verifyChain` to accept `AuditRecord<string>`.
That was enough for the *verification* half, which is why P4.5's canonical formats work. It was not
propagated to the *append* half.

```
AuditSealer          = (previous: ChainHead | null) => AuditRecord   // closed default
AuditRepositoryPort.appendChained(tenantId, seal: AuditSealer, …)
AuditSinkPort.write(record: AuditRecord)
AuditService.write(event: SecurityEvent)                             // closed union
```

Every one is pinned to `SecurityEventName`. The compiler states it plainly:

```
Type '(previous: ChainHead | null) => AuditRecord<string>' is not assignable to type 'AuditSealer'.
```

So a product with its own vocabulary can verify a chain through the Platform but can never append to
one. `DOCUMENT_DOWNLOADED` cannot pass through `appendChained`, and casting it to a Platform security
event is both the workaround this phase forbids and a false name in the evidence.

This is unfinished work from P3.7 rather than a design disagreement: the parameter exists, it simply
does not reach four declarations.

### Blocker P-9 — `AuditService` cannot mint the product's record id

`AuditServiceOptions` has no `generateId`. `AuditService` mints
`aud_${sequence.toString(36)}_${hash.slice(0, 12)}` unconditionally.

Munaxa Docs' digest **covers** its record id — a `uuidv7` assigned before sealing — which is the
entire reason P-6 exists. Adopting `AuditService` would therefore change both the id scheme and the
digest input for every new record.

`SessionManager` had exactly this problem and it was fixed in 2.1.0 by adding `generateId`. The same
one-line-shaped fix is missing here.

### What is *not* blocked

Worth stating clearly, because the brief expected these to be the risk:

| Concern | State | Why |
| --- | --- | --- |
| **Gap-free sequence** | **Fine** | `appendChained`'s contract puts the head read inside the adapter's transaction. Docs' `pg_advisory_xact_lock` and `tail + 1` stay in the adapter, exactly where they are today. |
| **`tail + 1` allocation** | **Fine** | `AuditService`'s sealer computes `previous === null ? 1 : nextSequence(previous.sequence)` — the same allocation, and bigint-safe since P-1. |
| **Transaction participation** | **Fine** | `AuditAppendOptions.transaction` exists, and Docs' ambient unit of work means the adapter simply calls `requireTransaction()`. No nested transaction, no independent commit. |

So the writer migration is blocked on identity and vocabulary, not on any of the guarantees that
make the trail evidentially valid. That is a better failure than the alternative.

## 2. Transaction Integration Report — **Not started**

Unblocked in principle; not attempted, because it cannot be done without the writer moving. Docs'
writers already run inside the caller's unit of work, so nothing about the current behaviour
violates the phase's requirements — audit writes participate in the caller's transaction today, do
not nest, and roll back with it.

### Filed as Platform limitation P-8

> The vocabulary type parameter added in P-7 reaches `AuditRecord` but not `AuditSealer`,
> `AuditRepositoryPort`, `AuditSinkPort` or `AuditService`. A product with its own event vocabulary
> can verify a chain through the Platform but cannot append to one.
>
> Suggested: propagate `TName extends string = SecurityEventName` through those four declarations.
> Defaulted, so every existing signature is unchanged. `verifyChain` was already widened this way in
> P-7, so the pattern is established.

### Filed as Platform limitation P-9

> `AuditService` mints `aud_${sequence}_${hash…}` with no way to supply a product's own id. A
> product whose digest covers an independently minted id — the case P-6 was built for — cannot use
> `AuditService` without changing both its id scheme and its digest input.
>
> Suggested: `AuditServiceOptions.generateId?: (sequence, now) => string`, defaulting to the current
> scheme. `SessionManager.generateId` solved exactly this in 2.1.0.

---

## Recommendation

P-8 and P-9 are both small, additive and defaulted — the same shape as the fixes already shipped in
2.1.0 and 2.2.0. Together they are one Platform release, after which this phase resumes with no
change to its plan: the adapter keeps the advisory lock and `tail + 1`, the Platform takes over
sealing, hashing and chain linkage, and the local writers are deleted.

Nothing here weakens an existing guarantee, and nothing was worked around.
