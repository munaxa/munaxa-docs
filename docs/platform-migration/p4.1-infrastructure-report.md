# P4.1 — Infrastructure layer adoption

**Status: the integration safety net is established and green. Cache is fully migrated.
Configuration, logging, shared types and remaining interfaces are not started.**

This phase led with "integration tests first", and that turned out to be the whole value of it —
the suite caught a regression on its first run that the unit tests were structurally incapable of
finding. The migration work that followed is smaller than the phase scope asks for, and §6 says
exactly what remains.

### The environment, for reproducibility

Docker is unavailable in this environment, so the compose stack was reproduced natively and
faithfully — same PostgreSQL major version, same roles, same ordering:

```
initdb -U edms_owner                       # cluster
psql -f infra/sql/cluster/01-roles.sql     # edms_owner + edms_app (no BYPASSRLS)
EDMS_APP_PASSWORD=… 02-app-credentials.sh
psql -f infra/sql/database/01-grants.sql   # per-database grants + tenant function
prisma migrate deploy                      # as edms_owner
psql -f infra/sql/post-migrate/*.sql       # RLS, audit immutability, content gate, workflow integrity
```

The post-migrate step matters: without it the row-level-security policies and the audit
append-only trigger are absent, and a suite that runs without them is not testing the thing that
makes tenant isolation and audit immutability true.

## 4. Integration test report

**584 passed, 7 skipped, 0 failures** across 33 files, against real PostgreSQL 16 and Redis.

The first run was **575 passed, 1 failed, 1 file unable to load**. Both problems were real and both
came from the migration, which is the point of running it:

### Failure 1 — a DI regression the unit tests could not catch

```
Nest can't resolve dependencies of the PlatformRedisCacheAdapter (Symbol(AppConfig), ?).
```

`PlatformRedisCacheAdapter` took `client?: Redis` so a test could inject a key-prefixed client.
Nest reads the second constructor parameter as a dependency **regardless of the `?`**, tried to
resolve `Redis` as a provider, and failed to construct `InfrastructureModule`. Every test that
boots the container failed to load.

The unit suite stayed green throughout, because it never touches the Nest container. That is
precisely the class of defect an integration suite exists for, and it would have reached
production as "the application does not start".

Fixed with `@Optional()`.

### Failure 2 — a stale assertion, and a chance to strengthen it

```
expected '$scrypt$v=1$n=131072,r=8,p=1$iuqAqi8u…' to match /^scrypt\$/
```

The provisioning test pinned the pre-migration hash format. New hashes are platform PHC, so the
assertion was stale rather than wrong. It now pins `$scrypt$v=1$n=131072,r=8,p=1$` — the format
**and** this product's cost parameters, so a future change that silently adopts the platform's
lighter N=2¹⁴ default fails here instead of shipping weaker passwords quietly.

### Standing caveat

The 7 skipped tests and 1 skipped file were skipped before this work; they were not investigated.

## 5. Platform consumption report

**Consumed:** `@munaxa/crypto` (password hashing), `@munaxa/interfaces` (`CachePort`),
`@munaxa/cache` (`MemoryCache` as the test double), `@munaxa/conformance` (adapter verification).

**Adapters:** `PlatformRedisCacheAdapter` — 13/13 on `runCacheConformance` against real Redis,
including `setIfAbsent` and `compareAndSet`. Neither existed on the retired local port, so MFA
replay protection, one-time codes and notification deduplication are now *possible* to wire where
before they were not.

**Compatibility layers:** one, deliberate. `LegacyScryptVerifier` reads `scrypt$…` hashes written
before the migration. Verify-only, so nothing new enters the old format; `needsRehash` is true for
all of it, so the existing upgrade-on-sign-in path retires the estate without a forced reset.
Delete when no `scrypt$` rows remain.

**No platform defects were discovered in this phase.** Both failures were in Munaxa Docs.

### Later phases, unchanged

P4.2 security + logging · P4.3 RBAC + sessions · P4.4 authentication ·
P4.5 audit · P4.6 cleanup and compliance audit.

**P4.5 stays blocked on platform work.** Audit chain migration requires `bigint` sequences, a
pluggable canonical form so three generations of historical digests keep verifying, and an
`appendChained` that can join the caller's ambient transaction. Filed as platform P-1. Munaxa
School and Munaxa Work will hit it identically, so it is worth fixing once in the platform rather
than three times in products.

### Two notes for whoever continues

**Session concurrency (P4.3) must land with enforcement.** Either implement
`SessionStorePort.createWithinLimit` in the Prisma store or wire a `LockPort`. With neither,
`SessionManager.limitEnforcement` reports `best-effort` and the limit is a hint — the platform's
own distributed suite asserts the overshoot rather than hiding it.

**Run the integration suite after every migration from here on.** It is now the only gate that
exercises the Nest container, row-level security and the audit trigger together, and it has
already paid for itself once.
