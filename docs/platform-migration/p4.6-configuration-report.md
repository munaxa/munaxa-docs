Platform 2.3.0, consumed from GitHub Packages. `@munaxa/config` added as a dependency; no
workspace references, no tarballs, no overrides, no local paths, no deep imports.

## A correction to the brief's premise

The brief lists **audit verification** among the capabilities already adopted. It is not.
P4.5C migrated the audit *writer*; `audit-verification.service.ts` and `hash-chain.ts`'s
`verifyChain` still recompute the chain locally, and the P4.5C report classified that item
"Not started". Nothing in this phase depended on it, so the correction is recorded rather than
acted on, and it stays the top adoption opportunity below.

# 1. Configuration Migration Report — **Completed**

Ten settings moved from the product's zod schema to `@munaxa/config`. One hundred stayed.

| Platform field | Read from | Lands at |
|---|---|---|
| `MUNAXA_SIGNING_SECRET` | `JWT_ACCESS_SECRET` | `auth.accessSecret` |
| `MUNAXA_REDIS_URL` | `REDIS_URL` | `redis.url` |
| `MUNAXA_LOG_LEVEL` | `LOG_LEVEL` | `log.level` |
| `MUNAXA_TOKEN_ISSUER` | `JWT_ISSUER` | `auth.issuer` |
| `MUNAXA_SESSION_MAX_CONCURRENT` | `SESSION_MAX_CONCURRENT` | `auth.maxConcurrentSessions` |
| `MUNAXA_TRUSTED_ORIGINS` | `CORS_ORIGINS` | `http.corsOrigins` |
| `MUNAXA_ACCESS_TOKEN_TTL` | `fromSeconds(JWT_ACCESS_TTL_SECONDS)` | `auth.accessTtlSeconds` |
| `MUNAXA_REFRESH_TOKEN_TTL` | `fromSeconds(JWT_REFRESH_TTL_SECONDS)` | `auth.refreshTtlSeconds` |
| `MUNAXA_SESSION_IDLE_TIMEOUT` | `fromSeconds(SESSION_IDLE_TTL_SECONDS)` | `auth.sessionIdleTtlSeconds` |
| `MUNAXA_SESSION_ABSOLUTE_TIMEOUT` | `fromSeconds(SESSION_ABSOLUTE_TTL_SECONDS)` | `auth.sessionAbsoluteTtlSeconds` |

The division is ownership, not size. The Platform knows what a session timeout *is* — that it has
an idle deadline and an absolute one, that a signing secret is key material rather than a word. It
has no view on how many pages a preview may render, which CSV profile an evidence bundle is
written under, or whether the cloud profile may run on a local filesystem, and it should never
acquire one.

**Three problems had to be solved for this to be adoption rather than a rename.**

**Units.** These variables have counted whole seconds since Phase 1; the Platform's fields are
durations in milliseconds. `fromSeconds()` restates the encoding *at the source*, so
`JWT_ACCESS_TTL_SECONDS=900` feeds a field that parses `15m` without the Platform relaxing what it
accepts. `AppConfig` still states seconds, so no consumer moved.

**Bounds.** The Platform's `MUNAXA_ACCESS_TOKEN_TTL` is a duration with no ceiling; this product
has refused an access token longer than an hour since Phase 1. Adopting the field and dropping the
bound would have been a weakening dressed as a migration. Every product bound is restated as a
`defineConfig` refinement, so it still fails at startup, in the same aggregated message, naming
the variable the operator actually set.

**Defaults.** Four of the ten default differently in the Platform. `MUNAXA_SESSION_IDLE_TIMEOUT`
is fifteen minutes there and eight hours here; an installation that never set the variable would
have started signing its users out every fifteen minutes. Those four are supplied through the
*source* (`withDocsDefaults`) rather than by redefining the field — redefining a Platform field is
refused, and rightly, because a product quietly overriding what the Platform says a session
timeout means is how a security setting stops meaning what it says. A default is not a meaning.

The subtlety that could have bitten: `parseConfig` reads a field's own key *before* its aliases,
so injecting `MUNAXA_SESSION_IDLE_TIMEOUT` while the operator had set `SESSION_IDLE_TTL_SECONDS`
would have silently discarded what they set. `withDocsDefaults` checks the canonical name and
every alias before filling in. There is a test for exactly this.

# 2. Platform Configuration Consumption Report — **Completed**

Every tool the brief named is used, and each earns its place:

| Tool | Where | Why |
|---|---|---|
| `PLATFORM_SCHEMA` | `platform.ts` | The base |
| `pickSchema()` | twice | Ten of twenty-five fields; and again to exclude secrets from the diagnostic rendering |
| `remapSchema()` | once | Every legacy variable name and landing path |
| `fromSeconds()` | four fields | The seconds-to-duration crossing |
| `defineConfig()` | once | The product's bounds as refinements |
| `nestConfig()` | `describePlatformConfig` | The startup line names settings the way the app does |
| `parseConfig()` | `loadPlatformConfig` | The parse |

**`extendConfig()` is deliberately not used.** It composes a product's fields *onto* the Platform
schema in the Platform's DSL — the right shape when a product is adopting the DSL wholesale. This
product has a hundred fields in zod with cross-field rules spanning them, and the brief forbids
rewriting product configuration. Using `extendConfig` would have required porting all hundred.
Two parsers, one aggregated failure, is the honest expression of "Platform validates Platform
configuration; Munaxa Docs validates Docs configuration".

`redactConfig()` is also unused, for a stronger reason: the startup diagnostic excludes secrets by
construction instead. A field that is not in the object cannot leak from it however that rendering
is later reused — and `MUNAXA_REDIS_URL` is excluded too, because `redis://user:pass@host` is a
credential the schema does not mark as one.

# 3. Product Configuration Report — **Completed**

One hundred settings stayed in `configuration.ts`, and they should. They divide into:

- **EDMS behaviour** — preview render caps, OCR languages, evidence-bundle CSV profile, reporting
  export bounds, search debounce and body limits, ACL cache and walk bounds.
- **Deployment topology** — the tenant catalogue and its three shapes, database pool sizing and
  per-process tenant-client bounds, deployment profile.
- **Driver selection and its consequences** — storage, mail, antivirus, OCR, office, metrics, and
  the rules about which are acceptable in production.
- **Product cross-field rules** — the cloud profile requires a catalogue and refuses a local
  filesystem; a remote storage driver requires a bucket and both halves of a key pair or neither;
  production refuses placeholder drivers, plaintext SMTP, the OpenAPI explorer, and insecure
  outbound HTTP.

`JWT_AUDIENCE` is the one JWT setting that stayed, and the reason is worth stating.
`MUNAXA_TOKEN_AUDIENCE` is a **list**, because a platform token may be presented to several
services. This product compares `payload.aud` to a single string. Widening `auth.audience` to an
array would change the shape `AppConfig` exposes and the meaning of that comparison — a rewrite of
the token service dressed as a configuration migration.

`NODE_ENV` also stayed, rather than adopting `MUNAXA_ENV`. Two reasons, and the first is decisive:
the Platform defaults it to `production` and this product defaults it to `development`, so an
installation that never set it would have flipped into production validation and refused to boot
on a driver it had always been allowed. The second is that `NODE_ENV` here is the trigger for
roughly a hundred lines of *product* production rules about storage, mail and OpenAPI — not
Platform rules. It is a product input that happens to share a name.

P1's caveat, unchanged from P4.5C: the product's `BreakReason` distinguishes `DIGEST_MISMATCH`,
`LINK_MISMATCH` and `SEQUENCE_GAP`, where the Platform has one flat `reason` string. Those are
three different accusations — a field was altered, a record was removed from the middle, a record
was removed and took its link with it — and an evidence bundle must not lose the distinction.
Either map back, or raise it upstream (see C).

## C. Potential future Platform enhancements

These are things this migration wanted and the Platform does not offer. Each is small and each
came out of doing the work rather than reading the source.

1. **A default override.** `remapSchema` changes where a field is read from and where it lands,
   but not its default — so a product whose historical default differs from the Platform's must
   inject one through the source, as `withDocsDefaults` does. That works and is explicit, but the
   table has to be maintained against the Platform's defaults, and nothing fails if the Platform
   changes one. A `withDefaults(schema, { FIELD: value })` beside `remapSchema` would make this a
   declaration instead of a workaround. **This is the single largest friction in the phase** — it
   is why four of the ten fields needed special handling.

2. **`redactConfig` should compose with `nestConfig`.** `redactConfig` returns
   `Record<string, unknown>` and `nestConfig` requires `Resolved<S>`, so rendering a redacted
   *nested* view needs a cast. Excluding secrets by construction avoided it here, but the natural
   composition should type-check.

3. **A richer verification reason.** As above: `DIGEST_MISMATCH` / `LINK_MISMATCH` /
   `SEQUENCE_GAP` are different accusations and the Platform's flat string cannot carry them.

4. **A metrics label catalogue.** Bounded label sets are a real control — a tenant id as a label
   is an unbounded cardinality explosion that takes the backend down during the incident it was
   added for. The Platform's `MetricsPort` has no way to express it.

## D. Follow-up unrelated to the Platform

`outbox-dispatch.integration.spec.ts > skips rows another dispatcher is holding` is flaky under
parallel load, on this branch and on the pre-change tree alike. The fixed 100 ms sleep waiting for
another connection to take a row lock should become a poll on `pg_locks`.

## The pattern, restated

P4.5C noted that four consecutive Platform releases were each unblocked by a missing generic found
by a consumer one release later. This phase is the first where the Platform had already shipped
what was needed — `pickSchema`, alias `decode` and schema-level refinement all landed in 2.1.0
*because* a consumer survey found them before the code was written. The one thing that survey
missed was the default override, and it is exactly the thing that cost the most here.

The lesson holds: survey the consumer before writing the Platform code, and survey it for
**defaults**, not only for names and types.
