# P4.2 — Configuration & observability adoption

**Logging is migrated. Configuration is blocked on a genuine Platform limitation and was not
worked around.** Shared-types and utilities assessments are below; both were scoped to proposals,
as the phase asked.

---

## 1. Configuration migration report — **blocked, not attempted**

Per this phase's rules, a Platform limitation is stopped on and documented rather than worked
around inside Munaxa Docs. This is one.

### The evidence

| | Docs `core/config` | `@munaxa/config` |
| --- | --- | --- |
| Variables | 107 | 25 (`PLATFORM_SCHEMA`) |
| **Overlap** | — | **0** |
| Naming | `APP_NAME`, `DATABASE_URL`, `REDIS_URL`, … | `MUNAXA_ENV`, `MUNAXA_LOG_LEVEL`, `MUNAXA_ACCESS_TOKEN_TTL`, … |
| Output shape | nested `AppConfig` (`config.app.name`, `config.acl.cacheTtlSeconds`) | flat `Resolved<Schema>` |
| Validation | zod, with cross-field refinements | per-field definitions |

Three independent blockers, any one of which is sufficient:

**Variable names.** `PLATFORM_SCHEMA` hard-codes the `MUNAXA_*` namespace. Adopting it renames
every environment variable in every deployment — Helm values, App Service settings, `.env` files,
CI secrets. This phase requires preserving deployment compatibility, and the platform offers no way
to map an existing name onto a platform field.

**Output shape.** `parseConfig` returns a flat record. Docs consumes a nested `AppConfig` across
the codebase. Flattening it is a rewrite of every consumer, not a configuration migration.

**Cross-field validation.** Docs' schema uses zod refinements — settings required only under a
given deployment profile, mutually exclusive tenant-catalogue sources. Per-field `FieldDefinition`
cannot express a rule spanning two fields, so those checks would have to move somewhere else and
stop being part of the schema.

### The correct boundary, once the limitation is fixed

`@munaxa/config` is built for *platform-owned* settings — session timeouts, password policy, CSP,
lockout — plus tenant overrides, secrets and feature flags. It is not a general-purpose
application-config framework, and treating it as one would be the mistake here.

The end state is a split, not a replacement: Docs consumes `PLATFORM_SCHEMA`, `TENANT_OVERRIDABLE`,
`EnvSecrets`/`CachingSecrets` and `FeatureFlags` for the ~25 platform settings, and keeps its own
zod schema for the ~100 Docs-specific ones (storage, OCR, retention, preview, search). That is a
boundary, not duplication.

### Filed as Platform limitation P-4

> `@munaxa/config` cannot be adopted by a product with existing deployments. `PLATFORM_SCHEMA`
> fixes both the variable names and the flat output shape, and `FieldDefinition` cannot express
> cross-field validation. A product must either rename every deployment variable or not adopt it.
>
> Suggested: allow a per-field `env` alias so `MUNAXA_LOG_LEVEL` can read `LOG_LEVEL`; allow a
> nesting hint or expose a mapper from flat to nested; add a schema-level `refine` for cross-field
> rules. Munaxa School and Munaxa Work will hit this identically.

## 2. Logging migration report — **done**

`core/observability/logger.ts` is now backed entirely by `@munaxa/logging`.

**Removed:** pino from the dependency graph; the hand-maintained `REDACTED_PATHS` list.

**Gained, and this is the substantive part.** The platform's `defaultRedactor` covers a strict
superset of the fields Docs named. The local list had 13 paths; the platform's has 20+, adding
`x-api-key`, `clientsecret`, `otp`, `totp`, `mfacode`, `sessionid` and `csrftoken`. Several of
those appear in this codebase and none were caught before — every one is a credential or a
second-factor value that could previously have reached a log line.

**What was kept, and why.** The four level methods (`debug`/`info`/`warn`/`error`) remain, over
152 call sites in 55 files. Rewriting each to `LoggerPort.log('info', …)` is churn with no
behavioural payoff and a real risk: `.error(` matches plenty of receivers that are not loggers, so
a regex sweep would have silently corrupted unrelated code. What remains is an adapter that
forwards — there is no logging logic in this repository any more. Migrating call sites to
`LoggerPort` directly is in the backlog (§10), not quietly skipped.

**Metrics untouched**, as required. `metrics.ts`, `metrics-registry.ts`, `metrics.sampler.ts` and
`metrics.controller.ts` (382 lines) stay product-owned because the platform deliberately does not
own metrics. Logging and metrics are now cleanly separated: `logger.ts` imports nothing from the
metrics files and vice versa.

**Correlation IDs and request logging** were not changed. `trace-context.ts` (119 lines) and
`request-observability.interceptor.ts` (122 lines) still use the local implementation. The platform
has `withCorrelation`/`currentCorrelationId` in `@munaxa/logging`, and adopting them is a real
follow-up — it was not attempted here because it touches the request pipeline, and this phase's
remaining budget was better spent leaving the suite green than half-migrating the interceptor.

## 3. Shared interface migration report — **partial**

`CachePort` comes from `@munaxa/interfaces` (P4.1). `LockPort` was the stated priority for this
phase and was **not** migrated.

`ports/cache.port.ts` still declares a local `LockPort`/`Lease`. The platform's `LockPort` differs:
it takes a lease in milliseconds and returns a `LockHandle` carrying a **fencing token**, which the
local `Lease` has no concept of. That is a genuine improvement — a holder that stalls past its
lease must not be able to release a lock a second holder now owns — but adopting it changes the
shape every caller destructures, and the correct time to do it is alongside session concurrency in
P4.3, where the lock actually matters.

## 4. Shared types assessment — proposal only

`@edms/domain` provides branded ids via `asId`/`AnyId`; `@munaxa/types` provides its own branded
`TenantId`, `UserId`, `SessionId` and friends via `unsafeId`.

| Type | Docs | Platform | Verdict |
| --- | --- | --- | --- |
| `TenantId` | `@edms/domain` | `@munaxa/types` | **Conflicting.** Both branded, structurally identical, nominally distinct. Casts required at every boundary today. |
| `UserId` | `@edms/domain` | `@munaxa/types` | Conflicting, same shape |
| `CorrelationId` | local string | `@munaxa/types` | Platform equivalent exists |
| Document/Revision/Folder ids | `@edms/domain` | — | **Keep product-specific.** No platform equivalent and there should not be one. |
| `AuditOutcome`, `AuditSubjectType` | `@edms/domain` | partial overlap with `SecurityEvent` | Defer to P4.5 with the audit chain |

**Migration impact: high, and it should not be done as its own phase.** The conflict is nominal
rather than structural, so it produces no runtime risk — but it means a cast at every call that
crosses into a platform service. The casts are currently invisible because so few platform services
are wired.

**Proposal:** do not migrate branded types standalone. Adopt `@munaxa/types` ids incrementally as
each capability migrates — `UserId`/`TenantId` land with authentication in P4.4, audit types with
P4.5 — so each change is validated by the tests for the capability it belongs to. A big-bang type
swap across 115,000 lines has no test that proves it correct.
