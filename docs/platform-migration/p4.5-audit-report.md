# P4.5 — Audit platform adoption

**Blocked.** The migration cannot be performed without failing this phase's own mandatory
requirement — that every historical audit record continues to verify — and the two things standing
in the way are Platform limitations this phase forbids fixing.

No code was changed. Nothing was half-migrated. The reasoning is below in full, because a blocked
phase is only useful if the next person can check the finding rather than take it on trust.

---

## 1. Audit Migration Report — **Blocked**

### Blocker A — a Platform canonical format cannot see the record id

This is the decisive one.

Munaxa Docs' digest covers `eventId` in **all three** of its chain-hash versions. It is the first
field after `previousHash` in the hashed material:

```ts
const material = [previousHash, event.eventId, event.tenantId, event.occurredAt.toISOString(), …];
```

`eventId` is an independently assigned `uuidv7`, minted before the digest is computed
(`chained-audit.writer.ts:71`). It is not derived from anything.

The Platform hands a canonical format exactly four things:

```ts
export interface CanonicalInput {
  readonly event: SecurityEvent;
  readonly previousHash: string | null;
  readonly recordedAt: number;
  readonly sequence: AuditSequence;
}
```

There is no `id`. The omission is deliberate and, for the Platform, correct — its own record id is
`aud_${sequence}_${hash.slice(0, 12)}`, genuinely derived from the digest, so a format able to read
it could hash its own output. That reasoning simply does not transfer to a chain whose id is
assigned independently and covered by the digest on purpose.

The consequence is exact: **no `CanonicalFormat` can reproduce a single historical Munaxa Docs
digest**, because the bytes it must produce contain a value it is never given. `verifyChain` would
report every existing record as tampered. Since P-1's whole design is that history is verified by
the format that sealed it, and that format cannot be expressed, historical verification through the
Platform is not merely difficult here — it is unrepresentable.

### Blocker B — the event vocabulary is closed, and the record is narrower

`SecurityEventName` is a closed union of **52** platform security events. Munaxa Docs writes **79**
audit actions across 13 modules — `CHECKED_IN`, `NUMBER_ASSIGNED`, `BULK_DOWNLOAD`,
`RETENTION_APPLIED`, `WORKFLOW_APPROVED`. These are document-management compliance events. They are
not security events, and a closed security vocabulary is the wrong home for them — that closure is
a deliberate Platform property ("one query works across every product") and opening it to admit a
document-management action would destroy the property rather than extend it.

Separately, four fields Munaxa Docs deliberately made **columns so the digest would cover them**
have no structural home in `SecurityEvent`:

| Field | Why it is a column here |
| --- | --- |
| `channel` | which surface acted |
| `onBehalfOfId` | delegation puts a second identity on the act |
| `reason` | a confidentiality level can *require* a stated reason |
| `apiClientId` | "which credential did this" is the first question an incident asks |

The schema comment on `apiClientId` states the principle plainly: *"a column the digest does not
cover is a column somebody with write access can change without breaking anything."* Pushing them
into `payload` would keep them hashed, but it would abandon the structural guarantee that made them
columns.

### What was considered and rejected

| Option | Why not |
| --- | --- |
| Register Docs' v1/v2/v3 as `CanonicalFormat`s | Impossible — Blocker A. The bytes require `eventId`. |
| Migrate only the 19 identity/security actions | Splits one trail into two and **breaks the gap-free per-tenant sequence**, which is the entire argument that nothing was removed from the end of the chain. A real loss of evidentiary strength traded for a partial adoption. |
| Write new records in Platform format, keep old ones local | Two hashing regimes and two verifiers in one table, permanently. Strictly worse than today, and deletes nothing. |
| Cast Docs' actions to `SecurityEventName` | A compatibility hack, forbidden by this brief — and it would put a false name in the evidence. |

## 2. Historical Compatibility Report — **Preserved, by not migrating**

Every historical record still verifies, under the verifier that sealed it. Nothing was re-hashed,
rewritten, re-sealed or replaced — which is also what the audit table itself enforces: it refuses
`UPDATE` and `DELETE` to every role, owner included.

Worth recording plainly: **Munaxa Docs already implements P-1's architecture**, and arrived at it
independently.

| P-1 capability | Platform | Munaxa Docs today |
| --- | --- | --- |
| bigint sequences | `AuditSequence` | `sequence BigInt`, gap-free |
| Versioned canonical serialization | `CanonicalFormat` + `formatVersion` | `chain_hash_version` 1/2/3, stamped per row |
| Historical verification by the sealing format | `verifyChain` dispatch | verification dispatches on each row's own stamp |
| Append inside the caller's transaction | `appendChained(…, { transaction })` | ambient unit of work, always |
| Serialised per-tenant append | store serialises | `pg_advisory_xact_lock` per tenant, `tail + 1` |

The version-appending discipline is the same too: v2 *appends* to v1's material and v3 to v2's, "so
a fourth version extends the material without moving a byte of what came before". That is the
Platform's rule for canonical formats, written independently in this repository first.

So the migration's upside was never new capability. It was consolidation — and consolidation is not
worth an unverifiable evidence trail.

## 5. Architecture Report

**Platform does not own audit, and after this phase still does not.** That is the honest statement.

Ownership after P4 → P4.5:

| Capability | Owner |
| --- | --- |
| Cache, crypto, logging, RBAC evaluation | Platform |
| Session lifecycle, deadlines, revocation, concurrency | Platform |
| Refresh issuance, rotation, replay protection | Platform |
| Access-token issuance | Munaxa Docs — carries Docs roles and permissions |
| **Audit chain, verification, serialization** | **Munaxa Docs** |
| Document-management business logic | Munaxa Docs |

No duplicated Platform functionality was introduced. No reverse dependency on Platform internals
exists. `@munaxa/audit` is not a declared dependency, which is the accurate reflection of the fact
that it is not used.

| Item | State |
| --- | --- |

| Configuration → `@munaxa/config` | **Not started** — unblocked since 2.1.0 |

| Legacy scrypt verifier removal | **Blocked** — correctly, until no `scrypt$` rows remain |

### Filed as Platform limitation P-6

> `CanonicalInput` cannot express a chain whose digest covers an externally assigned record id.
> The Platform excludes `id` because its own is derived from the hash; a consumer whose id is an
> independently minted UUID — and which therefore hashes it deliberately — cannot express its
> historical format at all, so P-1's historical-verification guarantee does not reach it.
>
> Suggested: pass the record id into `CanonicalInput` as an explicit, optional field. Formats that
> should not read it simply do not. The Platform's own v1 continues to ignore it, so no existing
> digest changes. Munaxa School and Munaxa Work will hit this identically if either hashes its own
> id.

### Filed as Platform limitation P-7

> `@munaxa/audit` models a *security* audit trail with a closed 52-name vocabulary. A product whose
> compliance trail is primarily domain events (79 here) cannot adopt it without either splitting
> its trail — losing a gap-free per-tenant sequence — or putting false names in the evidence.
>
> This may be correct scoping rather than a defect: a security audit trail and a
> document-management compliance trail are different artefacts that share a word, in the same way
> `SessionRecord` and `RefreshFamily` did. If so, the Platform should say so, and the expectation
> that every product migrates its audit trail should be retired rather than carried forward.

---

## Recommendation

Do not attempt this migration until P-6 is resolved. P-6 alone is small and additive, and it is
what makes historical verification expressible; P-7 is a scoping decision that should be made
deliberately rather than discovered by the next product.

Until then, Munaxa Docs' audit chain stays where it is — verifiable, transaction-integrated,
versioned, and gap-free.
