This phase completes what P4.7 stopped on. The audit trail is now Platform-owned end to end.

## 1. Audit Verification Migration Report — **Completed**

`audit-verification.service.ts` no longer verifies anything. It orchestrates: it reads the signed
checkpoint, walks the chain in batches, decides whether to write a new checkpoint, and raises the
alert. The recomputation is `@munaxa/audit`'s.

**The shape of the change.** The service now depends on a `CHAIN_VERIFIER` port, implemented by
`PlatformChainVerifier` in `infrastructure/`. A port rather than a direct call because the adapter
needs the row-to-record mapping, which lives in infrastructure, and the application layer may not
reach there — a rule `eslint.config.mjs` enforces and which is right.

**The walk got simpler, and safer.** It threaded `previousHash` and `cursor` as two variables;
they are one `ChainTail` now. That is not tidying: threading them separately is exactly what made
a record removed from the *front* of a batch invisible, because nothing compared the batch's first
position against where it was supposed to start.

```ts
const result = this.verifier.verify(slice.events, head);
head = { sequence: last.sequence, hash: last.hash };
```

**`verifyRange` preserved exactly.** The evidence-bundle path passed `{ from, fromSequence:
events[0].sequence }`. It now builds the equivalent head — the carried digest, at the position
immediately *before* the batch's first record — so the assertion is identical.

## 2. Checkpoint Verification Report — **Completed**

The signed checkpoint model is unchanged, and deliberately so.

`AuditCheckpointStore` still refuses a checkpoint whose HMAC does not recompute, with a key held
in neither the database nor the object store. The resume point is still read from it, and a range
that failed still refuses to produce one — a checkpoint written across a break would attest the
break as history, and the next pass would resume from inside it and find nothing wrong.

**What the Platform does with the head, and what it does not.** It verifies *from* the head it is
given. It cannot authenticate it — it has no way to tell a signed checkpoint from the first row of
the batch being verified, and taking the head from the batch would verify the batch against
itself. So trust in the resume point stays here, which is the one piece of audit verification this
product should still own.

Verified end to end: `verifies a chain the real writer appended, and checkpoints outside the
database`, `resumes from the checkpoint rather than re-walking the trail`, and `refuses a forged
checkpoint, so resuming cannot be steered` all pass against a real database.

## 3. Structured Failure Report — **Completed**

`BreakReason` moved to `modules/audit/application/ports.ts` and grew from three to five:

| Platform `code` | Product `BreakReason` | Tampering? |
|---|---|---|
| `DIGEST_MISMATCH` | `DIGEST_MISMATCH` | Yes — a field was altered |
| `LINK_MISMATCH` | `LINK_MISMATCH` | Yes — a record was inserted or removed mid-chain |
| `SEQUENCE_GAP` | `SEQUENCE_GAP` | Yes — a record was removed and took its link with it |
| `UNKNOWN_FORMAT` | `UNVERIFIABLE_FORMAT` | **No** |
| `MISSING_IDENTIFIER` | `UNVERIFIABLE_RECORD` | **No** |

The last two are renamed rather than folded in. That is the entire reason the mapping is written
by hand instead of passing the Platform's token through: `UNKNOWN_FORMAT` means the record could
not be checked, not that it was altered, and reporting it as `DIGEST_MISMATCH` would accuse
somebody of tampering on the evidence that this build did not recognise a format.

`isTampering()` is exported beside the type, and the alert branches on it — two different log
messages, and `tampering: boolean` in the payload. Both still fail the pass and both still refuse
a checkpoint, because a range that was not verified must not be attested as though it were. Only
one of them accuses anybody. The `auditChainBrokenEvent` payload documents the distinction so a
future notification consumer chooses severity from `reason` rather than from the event name.

**One thing this phase fixed rather than migrated.** `toPlatformRecord` throws on a
`chain_hash_version` it does not recognise — correct for the write path, wrong for verification,
where it would crash the pass and discard the finding for every row before it. The verifier now
stops the walk at the first such row, verifies everything before it normally, and reports
`UNVERIFIABLE_FORMAT` at that record. A break in the prefix is the earlier and more serious
finding and is reported instead; there is a test for that ordering.

with `chainHash` and verified with the Platform.** A test that sealed and verified with the

The gap spec was deleted **after** every gate passed, as instructed. It was written to fail once
the Platform gained a starting head; its job is done.

**What survives in `hash-chain.ts`, and why it is not duplication.** `chainHash`, `canonicalize`,
`GENESIS_HASH`, the three version constants, `isChainHashVersion`, `attestedFields` and
`ChainedEventInput`. None of them verifies. `chainHash` is kept for one reason and it is a good
one: `platform-canonical.spec.ts` asserts the Platform's formats reproduce *its* bytes rather than
a stored fixture. Deleting it would delete the comparison that proves the migration was sound.
`attestedFields` is the evidence bundle's manifest — a compliance artefact, not infrastructure.

## C. Future Platform enhancements

1. **A schema default override.** `remapSchema` changes where a field is read from and where it
   lands, but not its default. The largest friction in P4.6 — four of ten fields needed a
   hand-maintained defaults table.
2. **`redactConfig` should compose with `nestConfig`.** The natural composition needs a cast.
3. **A metrics label catalogue.** Bounded label sets are a real control the Platform cannot
   express, and the local implementation is the better one.
4. **A checkpoint contract.** Not urgent, and worth stating now that this phase has drawn the
   line: the Platform verifies *from* a head and correctly declines to authenticate it, but every
   product doing incremental verification will build the same signed-resume-point machinery. A
   `CheckpointPort` — sign, verify, store — with the key strictly the product's would be
   adoptable without the Platform ever holding trust it cannot justify.

## D. Follow-up unrelated to the Platform

`outbox-dispatch.integration.spec.ts > skips rows another dispatcher is holding` is flaky under
parallel load, on this branch and on the pre-change tree alike (confirmed in P4.6 by stashing and
re-running three times). Its fixed 100 ms sleep waiting for another connection to take a row lock
should become a poll on `pg_locks`.

## Closing note on the pattern

Five consecutive Platform releases were each unblocked by something a consumer found afterwards.
P4.7 is the one that was found *before* the workaround was written rather than after: the phase
stopped, documented the gap with an executable spec, and the Platform closed it additively in
P3.9. The cost was one extra release cycle. The alternative — flattening five failure codes into
three, or verifying seven years of trail from genesis every night — would have been permanent.

Stopping was the cheaper option, and it was only available because the limitation was expressible
as a test rather than an opinion.
