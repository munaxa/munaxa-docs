# P4.7 — Audit Verification Platform Adoption

## Outcome: **BLOCKED**

The migration was evaluated and not performed. `@munaxa/audit`'s `verifyChain` cannot express the
verification this product performs, and the shortfall is a capability rather than a diagnostic
nicety: **the platform's verifier can only start a walk at genesis, and this product never
verifies from genesis.**

The brief asked for exactly this evaluation, and for a stop rather than a flattening. No
product-specific workaround was introduced, no verification semantics were simplified, and no
Platform code was modified.

---

## The finding

`VerifyChainOptions` has one member:

```ts
export interface VerifyChainOptions {
  readonly formats?: CanonicalFormatRegistry | readonly CanonicalFormat[];
}
```

and `verifyChain` opens with `let previousHash = null; let expected = null;`. A chain is therefore
only verifiable as a whole, beginning at the record whose `previousHash` is `null`.

Every call this product makes passes a starting digest **and** a starting sequence:

```ts
verifyChain(slice.events.map(toLink), { from: previousHash, fromSequence: cursor + 1n })
```

There are two such call sites — the batched daily walk and the evidence-bundle range check — and
neither ever starts at genesis. `AUDIT_VERIFY_BATCH_SIZE` defaults to 5,000 and
`AUDIT_VERIFY_MAX_EVENTS` to 200,000, so even a single pass over a modest trail is forty batches,
thirty-nine of which begin mid-chain.

### Why this is not a diagnostic loss but an evidentiary one

Handing the platform a continuation batch does not fail to detect a break. It **fabricates** one:
the batch's first record chains to a digest the verifier has initialised to `null`, so the result
is `valid: false, reason: 'previous hash does not match the preceding record', checked: 0` — on
completely intact evidence.

`13-audit-architecture.md` §4 pages at the highest severity in the product on that result. A
verifier that raises it nightly is worse than no verifier, because it trains an operator to ignore
the one alarm that must never be ignored.

### Why the resume point cannot simply be dropped

Resuming from a checkpoint is not an optimisation. It is what makes the daily pass affordable over
a seven-year trail, and — more importantly — the checkpoint is **signed**. The store refuses to
return one whose signature does not recompute, so "start from sequence 84,213 with digest 9c2f…"
is a claim authenticated with a key held in neither the database nor the object store. That is the
whole of §4's *"an attacker with database access alone cannot rewrite history undetected"*.

Verifying from genesis every night would discard that argument along with the batching: the
verifier would take its starting digest from the rows themselves, which is precisely the data an
attacker with database access controls.

### Why `fromSequence` matters separately

The platform sets its expected sequence from the first record it is handed, so a record removed
from the **front** of a batch is invisible to it. This product passes the sequence the batch must
start at and reports `SEQUENCE_GAP` — the hole the hash alone cannot see, and the reason the
sequence column exists at all.

### The gap is not about digests

Worth stating clearly, because it bounds the problem: on a chain that *does* start at genesis, the
platform verifier and this product agree exactly, including on an altered field, a swapped record
id and a removed record, across all three Docs canonical formats. Everything P4.5C migrated works.
The single missing thing is a starting head.

### Evidence

`apps/api/src/core/audit/platform-verification-gap.spec.ts` — six tests, executed rather than
asserted, run against the published `@munaxa/audit@2.3.0`. It proves the agreement above, the
fabricated break on a sound continuation batch, the absent option, and the invisible front-of-batch
removal. It is written to fail loudly the moment the platform gains a starting head, at which point
it is deleted and the migration proceeds.

---

## The recommended Platform enhancement

**One optional field, reusing a type the platform already exports.** `@munaxa/interfaces` already
defines `ChainHead { sequence: AuditSequence; hash: string }`, and `AuditSealer` already takes
`ChainHead | null` on the append side. Verification should be symmetric:

```ts
export interface VerifyChainOptions {
  readonly formats?: CanonicalFormatRegistry | readonly CanonicalFormat[];
  /**
   * The head the first record must chain from, and the position it must occupy.
   * Absent means genesis — today's behaviour, unchanged.
   */
  readonly from?: ChainHead | null;
}
```

In `verifyChain`, `previousHash` initialises to `options.from?.hash ?? null` and `expected` to
`options.from === undefined ? null : nextSequence(options.from.sequence)`. Nothing else changes.

This is additive, defaults to current behaviour, breaks no existing caller, and closes the whole
blocker — `from` and `fromSequence` in one field, because a head is both.

### A second, smaller enhancement — diagnostics

Not blocking on its own, and it would still be needed for this product to migrate without losing
evidence quality:

| This product reports | The platform reports |
|---|---|
| `reason: 'DIGEST_MISMATCH' \| 'LINK_MISMATCH' \| 'SEQUENCE_GAP'` | one unversioned prose string |
| `expectedHash`, `actualHash` | neither |
| `brokenAt`: the record **id**, which an auditor looks up | `brokenAt`: the sequence |

The information for the first row exists in the prose, but recovering an enum by matching on an
unversioned message would be exactly the product-specific workaround the brief forbids. Suggested,
all additive:

```ts
export type ChainBreak =
  | 'DIGEST_MISMATCH' | 'LINK_MISMATCH' | 'SEQUENCE_GAP'
  | 'UNKNOWN_FORMAT' | 'MISSING_IDENTIFIER';

interface ChainVerification {
  // …existing fields unchanged…
  readonly code?: ChainBreak;
  readonly brokenAtId?: string;
  readonly expectedHash?: string;
  readonly actualHash?: string;
}
```

Three accusations are three different responses. A digest mismatch means a field was altered; a
link mismatch means a record was inserted or removed mid-chain; a sequence gap means a record was
removed and took its link with it. Collapsing them would be a loss of evidence, not of polish.

## Deliverables

### 1. Audit Verification Migration Report — **Blocked**

Evaluated, not performed. `verifyChain` cannot begin a walk anywhere but genesis; this product
never begins one there. Documented above with executable evidence and a two-line additive
enhancement.

**Partial adoption was explicitly rejected.** Using the platform for whole-chain verification and
keeping the local implementation for slices would leave two verification implementations, which
the brief forbids and which is worse than either alternative: two answers to "is this evidence
sound", diverging silently.

### 2. Historical Compatibility Report — **Completed** (unchanged, and re-run)

Nothing was migrated, so nothing could regress. Every historical compatibility test was re-run and
passes, and the new gap spec adds independent confirmation that the platform reproduces this
product's digests on genesis-rooted chains.

No record was rewritten, resealed, renumbered or rehashed. Historical bytes are identical because
nothing touched them.

### 3. Tamper Detection Report — **Completed** (unchanged)

Tamper detection is exactly what it was. The product's verifier still reports the three
accusations separately, still refuses a forged checkpoint, and still verifies each batch against
the digest carried forward rather than the one the batch supplies about itself.

The gap spec additionally establishes that the platform verifier detects an altered field, a
swapped id and a removed record on a genesis-rooted chain — so the blocker is scoped to the
starting head, not to detection strength.

### 4. Deleted Code Report — **Not started**

Nothing deleted, correctly. Deleting the local verifier without a replacement that can resume from
a signed checkpoint would remove the daily pass. `hash-chain.ts`'s `verifyChain` and
`audit-verification.service.ts` remain, and are not duplicates of anything: no platform
verification runs in this product.

### 5. Dependency Reduction Report — **Not started**

No dependency added or removed. `@munaxa/audit` was already a dependency from P4.5C.

## C. Future Platform enhancements

Ordered by how much they block, and every one found by doing the work rather than reading the
source.

1. **`VerifyChainOptions.from?: ChainHead | null`** — blocks P4.7 entirely. Two lines, additive,
   symmetric with `AuditSealer`'s existing `ChainHead | null`.
2. **Structured verification failures** — `code`, `brokenAtId`, `expectedHash`, `actualHash`.
   Needed for P4.7 to migrate without losing evidence quality.
3. **A schema default override** — `remapSchema` changes where a field is read from and where it
   lands, but not its default. The single largest friction in P4.6: four of ten fields needed a
   hand-maintained defaults table because of it.
4. **`redactConfig` should compose with `nestConfig`** — the natural composition needs a cast.
5. **A metrics label catalogue** — bounded label sets are a real control the Platform cannot
   express.

## D. Follow-up unrelated to the Platform

`outbox-dispatch.integration.spec.ts > skips rows another dispatcher is holding` is flaky under
parallel load, on this branch and on the pre-change tree alike (confirmed in P4.6 by stashing and
re-running). Its fixed 100 ms sleep waiting for another connection to take a row lock should become
a poll on `pg_locks`.

## The pattern, again

P4.5C observed that four consecutive Platform releases were each unblocked by a missing generic
found by a consumer one release later. P4.6 was the first phase where the Platform had already
shipped what was needed — because a consumer survey ran before the code was written — and the one
thing that survey missed (defaults) cost the most.

P4.7 is the same lesson at a different level. `verifyChain` was designed for the shape the Platform
verifies: a whole chain, in memory, from genesis. A consumer whose chain is millions of rows long
and verified nightly in batches from a signed resume point was never in view. The append side got
this right — `appendChained` hands the adapter the head precisely because the Platform knows it
does not own ordering. Verification is the same problem and did not get the same treatment.

**The recommendation for the Platform is not just the two lines. It is to survey the consumer for
how a capability is *operated*, not only for what it computes.**
