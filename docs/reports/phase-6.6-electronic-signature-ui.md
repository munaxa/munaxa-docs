# Phase 6.6 — Electronic Signature & Witnessed Attestation UI

**Status: BLOCKED** — on one specific, additive API gap, found in the Part 1 survey.

No UI was built. Part 15 requires stopping and reporting before changing an API contract, and the
gap below sits underneath the ceremony's central screen, so building around it would have meant
doing exactly what Part 3 forbids.

Both Phase 6.7 blockers really are closed — the partial unique index and the distributed rate limit
are in place and proven. This is a different, smaller obstacle, and it was not visible until the UI
requirements were read against the API surface.

---

## The gap: the canonical statement cannot be shown before signing

**Part 3 requires**, before confirmation, that the user sees *"the exact attestation statement
returned/generated by the existing backend"*, and adds: *"Do not paraphrase the attested statement
if the backend provides canonical text"* and *"Do not construct a different statement in the
browser."*

**The API cannot supply it.** `DocumentSignaturesController` has exactly four routes:

| Route | Returns `statementBody`? |
| --- | --- |
| `GET /documents/:id/signatures` | No — `toSignature` omits it deliberately |
| `POST /documents/:id/signatures` | No — same mapper |
| `GET /documents/:id/signatures/:signatureId/verification` | **Yes** — the only route that does |
| `POST /documents/:id/signatures/:signatureId/withdrawal` | No |

`statementBody` appears once in the contracts (`signature.ts:93`), inside the **verification**
schema. Verification requires a `signatureId`, which requires the signature to already exist.

`serialiseSignatureStatement` is called only inside `DocumentSignatureService.sign`, at the moment
of signing, from values the server resolves itself — the content digest read from the revision's own
blob, the signer's printed name and email *as they stand at that instant*, and the server's clock.
**There is no way to obtain the statement before the act that creates it.**

### Why the three workarounds are all refused

1. **Render it in the browser.** Forbidden by Part 3, and correctly so: ADR-0017 §3 stores the bytes
   verbatim precisely so verification never depends on regenerating them. A browser-composed
   statement would be a *different artefact* from the attested one, and showing it would make the
   ceremony display something other than what was signed.
2. **Sign first, then show it.** Inverts the ceremony. The user would attest before reading.
3. **Paraphrase.** Explicitly forbidden, and it is the evidence — §11.50's manifestation is the
   point of the whole design.

### The smallest additive solution

A preview route that serialises the statement without persisting anything:

```
GET /v1/documents/:id/signatures/statement?revisionId=…&purpose=…
→ { statementBody, documentNumber, revisionLabel, contentSha256, signerName, signedAtHint }
```

- **Additive**: new route, no existing shape changed, no permission added — `document:sign` plus the
  existing `@ScopedTo` document scope, so only somebody who may sign may preview.
- **Discloses nothing new**: every field is already visible to that caller through the document, the
  revision and their own profile.
- **Not the signed bytes**: the timestamp differs at the instant of signing, so the preview must be
  labelled as the statement's *shape and content*, not a byte-for-byte promise — or the route must
  accept the caller's intent and the server must re-serialise at sign time regardless, which it
  already does.

**Where it belongs:** a small backend phase, not this one. Part 15 says to report the gap and let
the decision be made rather than fold an API change into a UI phase.

## What is otherwise ready

The survey found no other obstacle. `POST` for signing, `GET` for the list, verification's three
booleans, and withdrawal all exist with the right permissions and scoping; `GET /v1/auth/mfa` tells
the UI whether the signer owes a TOTP code, so no new endpoint is needed for the re-authentication
step; and `429` already carries `retryAfterSeconds`. Once the preview exists, the remaining work is
ordinary UI against a complete contract.

## Deliberately not done

No UI, no signature-request states, no second MFA dialog, no API invented, no ADR change, no
Platform change. Nothing was built that would have to be unpicked.
